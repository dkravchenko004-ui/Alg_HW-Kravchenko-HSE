# Задача 1. Compare

## Условие

Рекурсивные mergesort и quicksort. Декоратор, который замеряет время
вызова. Тесты, на которых время этих двух сортировок заметно расходится.

Код: `solution.py`  
Тесты: `test_compare.py`

---

## 1. Объяснение решения

**Mergesort.** Делим массив пополам, сортируем половины, сливам.
Слияние идёт в вспомогательный массив: берём меньший из двух текущих
элементов. Если равны — берём из левой половины, чтобы слияние было
устойчивым. Рекурсия по индексам, не через срезы на каждом шаге: так
дополнительная память линейная, а не `O(N log N)` копий.

**Quicksort.** Как на лекции:

1. берём опорный элемент (здесь — **последний** на текущем отрезке);
2. меньшие оказываются **до** него, большие **или равные** — **после**;
3. те же два шага рекурсивно слева и справа от опорного.

Равные ключи не остаются «неизвестно где»: они уходят вправо от pivot.
Это то же правило, что в слайде, только зафиксирован выбор опорного.

Разделение — Lomuto: идём слева направо, меньшие меняем в начало
отрезка, в конце ставим pivot на границу.

**Декоратор `timed`.** Перед вызовом запоминаем `perf_counter`, после —
пишем разницу в `func.last_time`. Саму сортировку не печатаем, чтобы
тесты не засорялись. `@timed` висит на входных `mergesort` / `quicksort`,
а не на внутренних рекурсивных функциях: иначе каждый спуск заново
засекал бы время.

Исходную последовательность не меняем: работаем с копией.

**Некорректный ввод.** Не последовательность или не целые элементы —
`TypeError`. `bool` целым не считаем.

## 2. Оценка сложности

Пусть `N` — длина массива.

**Mergesort**

- Время `O(N log N)` всегда: глубина деления `log N`, на уровне `O(N)`
  работы на слиянии.
- Память `O(N)` на вспомогательный массив плюс `O(log N)` стек рекурсии.

**Quicksort**

- В среднем `O(N log N)` время, стек `O(log N)`.
- Худший случай `O(N^2)` время и стек `O(N)`: если массив уже
  отсортирован, а опорный всегда последний, каждая разбивка отрезает
  один элемент.
- Дополнительная память кроме стека `O(1)` (плюс копия входа).

**`timed`:** константа на один внешний вызов, асимптотику не меняет.

Именно худший случай quicksort даёт тест, где время «прилично»
отличается: mergesort на возрастающем массиве остаётся `N log N`,
quicksort уходит в `N^2`.

## 3. Визуализация работы алгоритма

Массив `[5, 2, 8, 1]`.

**Mergesort** — деление, потом слияние:

```text
[5, 2, 8, 1]
      /          \
 [5, 2]          [8, 1]
  /   \           /   \
[5]   [2]       [8]   [1]
  \   /           \   /
 [2, 5]          [1, 8]
      \          /
      [1, 2, 5, 8]
```

Слияние `[2, 5]` и `[1, 8]`: 1 < 2 → 1, потом 2 < 8 → 2, потом 5, 8.

**Quicksort**, опорный последний:

```text
[5, 2, 8, 1]     pivot = 1
все остальные > 1, уходят вправо
[1 | 2, 8, 5]    1 на месте

правая часть [2, 8, 5], pivot = 5
2 < 5 → налево, 8 >= 5 → направо
[1, 2, 5, 8]
```

**Почему времена разъезжаются.** Возрастающий `[0, 1, ..., 499]`,
опорный всегда максимум отрезка:

```text
pivot=499 → отрезали один элемент, осталось 499
pivot=498 → осталось 498
...
сравнений порядка 500 + 499 + ... ≈ 125000

mergesort на том же входе: около 500 * log2(500) ≈ 4500 сравнений
```

Декоратор как раз это показывает: `quicksort.last_time` больше
`mergesort.last_time` в разы. На случайном массиве оба близки к
`N log N`, разница уже не обязана быть большой.
